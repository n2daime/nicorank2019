## 変更提案のフロー（Issue 駆動）

新しい機能・変更の提案はこのファイルには記録しない。以下のフローで **GitHub Issue と `docs/tasks.md`** で管理する。

```
1. 提案    新しい機能・変更を GitHub Issue として登録する
2. 承認    Issue を確認し、実装するか判断する
3. 展開    承認後、docs/tasks.md にタスクとして展開する（Issue 番号と関連付ける）
4. 実装    タスクに従って実装する。仕様変更は docs/specs.md、設計判断は docs/design.md に反映
5. 完了    docs/tasks.md に完了マークを付け、Issue を Close する
```

## プロジェクト開発背景

このプロジェクトがなぜ存在し、なぜこのような形になったのかの記録。**将来の自分（保守担当者）に向けた備忘録であり、コードだけからは読み取れない情報を含む。**

### 成り立ち（2007年〜）

- **開発開始は 2007 年**。当時は 1 ファイルの C++ プロジェクトだった。
- 幾度かのリファクタリング・言語移行を経て、現在は C#（.NET Framework 4.8 主体）のソリューションになっている。
- 開発者の主な担当は週刊ニコニコランキング2代目（2026年現在）。
- ツールの目的は「**週刊ニコニコランキング**」および「**ニコニコランキングSP**」の集計。

### 開発体制と運用

- **ほぼ1人でコードを書き続けてきた**。長期にわたり知識がコードにしか残っていなかった。
- ランキングチームは**社会人中心の構成**。平日の作業時間が限られることが運用設計に影響している（後述の「中間集計」）。
- バージョン管理: 2007年〜2023年頃までは **SVN**、その後 **Git（GitHub）** に移行。
  - SVN 時代の残滓（C++ 版、2017〜2018年時点の状態）が開発者のローカル環境に存在する。2007年当時の情報は完全には残っていない。

#### 週刊ランキングの公開フロー（運用）

```
土日: 中間集計（仮集計）→ 事前準備（紹介位置の決定など）
月曜: 週刊集計 → 動画作成 → ニコニコに投稿
     → ニコランWeb管理画面で情報を手動アップロード → ニコランWebサイト更新
```

- **長期動画リスト**: 同じ動画 ID が複数回週刊ランキングに登場したときに、ランキング動画上で「ランキングN回目」と表示するための仕組み。
  - 一定回数以上登場する動画は**門番動画**扱いとなり、通常 20 位しか紹介しない枠を門番の数だけ拡張するルールがある。
  - 本ツールは `Output/長期動画リスト.txt` にランクイン回数付きで出力する。
- **ED枠**: 紹介できなかった 21 位以降（門番による拡張枠で変動）から 150 位くらいまでをサムネイル形式で紹介するパート。
  - 動画情報 → 画像ファイル化は**別ツール**で行っているため、本ツールからは情報を提供する txt ファイル（`rankED.txt`）を出力している。

### 集計モードの開発背景

#### 週刊集計（Weekly）

- 週刊ニコニコランキング初期は**マイリスト・コメント・再生の各ランキングしか存在せず、統合ランキングがなかった**。そのため独自の計算式で統合ランキングを作る必要があった。
- 現在は公式の統合ランキングが存在し、このツールの必要性自体は薄れている。
- ただし**公式ランキングは各種数字（再生数・コメント数等の内訳）を公開していない**ため、独自ランキングの需要は残っている。

#### 中間集計（Tyukan）

- 週刊集計は**月曜日に集計 → 動画公開**の流れだが、公開までに使える準備期間は平日のみ。
- 社会人中心のチーム構成では平日の作業が厳しいため、**土日に仮集計（中間集計）** を行い、上位動画の紹介位置などを事前に決めておけるようにした。
- 2024-06 に追加された「先週の基準日」設定は、中間集計・週刊集計で差分計算の基準日を変更できるようにする機能（設定できるのは月曜日のみ。基準日と同日・未来は無効値扱い）。

#### SP 集計（SP）

- 半期または年間のニコニコランキングSP動画を作成するための専用モード。
- 通常の週刊ランキングとは別の入力（動画IDリスト + スナップショットDB差分）を使う専用モード。

#### スナップショット集計（SnapShot / nicorank_SnapShot）

- ニコニコ動画の**全動画の再生数・コメント数・マイリスト数・いいね数**をスナップショット API から取得し、その差分を SP 集計などの基準データとして使う。
- 2007年3月以降の全期間を対象に、15日間隔で取得（直近1年は1000再生制限なし、それ以前は制限あり）。
- **差分方式を採る理由**:
  - 集計期間（半年〜1年）が長く、週刊ランキングのような前週比較ができないため、期間開始時と終了時のスナップショット累積値の差を取る方式。
  - 週刊ランキングの公式データは**取得件数に制限**があり、半年や1年単位の差分を比較したときに「片方の情報がない」ことが多々あった。
  - 差分計算できた動画・できなかった動画を同じ数字としてランキング計算するのは**結果の公平性の観点で問題**がある。
  - 過去は**手作業で差分情報を入力**していたが、スナップショット DB で自動化したのがこの方式の背景。

### 外部サービスとの関係

#### ニコランWeb（nicoranweb.com）

- 集計結果（`result_DB登録用*.csv` / `result_DB登録用*.json`）は**ニコランWeb の管理画面で手動アップロード**している。
- 自動連携ではないため、アップロードは週刊ランキング公開フローの一部として人が行う。

#### 過去ランキング JSON（自前運用の互換サイト）

- ニコニコ動画がサイバー攻撃を受ける前は、以下の公式サイトからランキングの過去ログを取得できた。
  - `https://dwango.github.io/niconico/genre_ranking/ranking_log/`
- サイバー攻撃後、**過去ログファイルが公式から提供されなくなった**ため、互換性をもったサイトを自前で運用している（個人 NAS 上。URL は公開しない）。
- nicorank_oldlog はこのサイト向けに過去ランキング JSON を収集・保存するツール。

#### ニコニコチャート（nicochart.jp）

- 基本的には不要だが、**公式チャンネル動画（`so` から始まる動画）は、非公開→再公開されると投稿日時が更新される**仕様（更新条件は不明）。
- 本ツールの DB は **2019 年以前の情報を持っていない**ため、それを補完するために連携している。
- 例: 2008 年に 100 万再生されていた動画が 2026 年に再公開された場合、差分情報が取れず「2026 年に 100 万再生した」という扱いになってしまう。実態に合わないため、2019 年以前の情報取得として nicochart.jp にアクセスしている。
- **アクセス条件は限定的**:
  - 対象は「公式チャンネル動画（so）で、かつ差分データが取得できない」場合のみ。
  - 取得は 1 動画につき `http://www.nicochart.jp/point/{id}.tsv`（1動画分のTSV）を 1 回だけ。取得成功後はローカル DB（`LogNicoChart.db`）にキャッシュし、以後は再アクセスしない。
  - アクセスは**単一スレッドの直列処理**（`SabunReader` の foreach ループ内から順に呼ばれる）。並列・連続アクセスはしない。
  - 通常の集計ではアクセスは発生しない（発生してもごく少数の動画に限られる）。
